# How safe is safe-pdf?

Reviewed on 23 November 2026 against commit `1c7927a` on `phase-9-gui`. The question is what happens when someone opens a PDF supplied by a person they do not trust, then reads, searches, annotates, or exports from it.

**The strongest assurance is in how safe-pdf interprets hostile bytes.** Its Lean core has no filesystem or network authority. It has machine-checked results for operations that have historically been difficult to get right in PDF readers, including following cross-references, bounding decompression, and resolving objects across revisions. The desktop viewer adds a native GUI, file operations, optional library synchronization, and concurrent rendering in the same process. **For higher safety, the two most valuable changes are to enforce resource limits across a whole user operation and to run document processing in a restricted process that the GUI can stop.** [Public API](../SafePdf/Api.lean) · [Viewer implementation](../SafePdf/Shell/App/Viewer.lean)

## What happens when a PDF is opened

| Stage | Protection in this revision | Where the guarantee ends |
|---|---|---|
| Read the bytes | The standalone viewer uses the inspector's loader. It checks the reported file size and caps the actual read at the input limit plus one byte. The pure parser checks the resulting byte array before opening it. | Library callers get a different file helper. `Api.openFile` checks metadata, then calls `readBinFile`. If the file grows, the allocation can precede rejection. Callers of `openBytes` have already acquired the bytes. [Inspector loader](../SafePdf/Shell/Inspect.lean) · [API](../SafePdf/Api.lean) · [Parse entry point](../SafePdf/Core/Parse.lean) |
| Parse objects | Lean checks termination. The lexer agrees with the project's list-based specification. The object-parser equivalence states the conditions on the remaining token stream. Nesting has an explicit cap, and parse failures are values callers can inspect. | These proofs describe the grammar safe-pdf implements. Agreement with the project's model and agreement with other readers are separate questions. [Lexer equivalence](../SafePdf/Spec/LexEquiv.lean) · [Object-parser equivalence](../SafePdf/Spec/ObjEquiv.lean) · [Recorded interpretation differences](deviations-from-spec.md) |
| Resolve references and revisions | The cross-reference walk tracks visited offsets and has a decreasing measure. A strict chain has at most one winning entry per object number, determined by the newest revision listing it. This matters when a saved PDF contains several versions of an object. | The uniqueness result concerns safe-pdf's resolution rules. A signed revision, a viewer using different precedence rules, and a repaired file each require their own interpretation. [Termination proof](../SafePdf/Spec/XrefTerm.lean) · [Revision precedence](../SafePdf/Spec/Unambiguous.lean) |
| Handle malformed input | Strict opening runs first. Structural cycle and encryption-setup errors are final. For other failures the reader may scan for object headers, reconstruct a trailer, validate the root, and return a document flagged as repaired. The scan bounds failed attempts and recorded objects. Its overall time analysis is informal. | Strict success wins. That gives a precise guarantee without assuming that independently scanning a valid PDF would reconstruct the same object graph. The API accepts repair by default. With `allowRepair := false`, it rejects a repaired result **after** parsing, so that option can still incur repair work. [Open and fallback](../SafePdf/Core/Open.lean) · [Repair bounds](../SafePdf/Repair.lean) · [Strict API result](../SafePdf/Api.lean) |
| Decompress streams | Byte filters include Flate, LZW, ASCII encodings, and RunLength. Theorems bound returned bytes and charge successful decodes against the budget threaded between calls. Structural streams used to open the document consume budget too. | For Flate, the bound on success or error is `3360 × input bytes + 3 × stream limit + 12163` modeled steps. CPU time also depends on the runtime and hardware. API calls for page text and rasterization each start a fresh budget. Repeated calls can therefore consume many times one budget. [Filter and budget theorems](../SafePdf/Core/Filter.lean) · [Flate cost model](../SafePdf/Spec/FlateWork.lean) · [Page API](../SafePdf/Api.lean) |
| Interpret and paint a page | The content interpreter produces a display list of drawing operations. Operator, nesting, form-expansion, glyph, and image limits bound specific kinds of work. JPEG and CCITT decoding are implemented in pure Lean. A successful API render has exactly four bytes per output pixel. | The directory named `Quarantine` is a source-code boundary. These codecs execute in the viewer process. Failed or unsupported images can become placeholders, and a capped form expansion can omit content with a warning. A well-shaped image can still show the wrong page. [Interpreter specification](../SafePdf/Spec/Content.lean) · [Limits and degradation rules](../SafePdf/Core/Limits.lean) · [JPEG](../SafePdf/Quarantine/DCT.lean) · [CCITT](../SafePdf/Quarantine/CCITT.lean) · [Raster API](../SafePdf/Api.lean) |

### What the size limits mean on a desktop

Defaults include 1 GiB of input, 256 MiB of decoded bytes per stream, 1 GiB of total decoded bytes for a threaded budget, eight filters per chain, 4,096 revisions, and ten million content operators per page. The core page-side cap of 16,384 permits a square RGBA buffer of **1 GiB**. The viewer separately reduces the requested zoom toward a 256 MiB page-image target and caps its image cache at 256 MiB. Four page-render jobs and two thumbnail jobs can be in flight. Input, temporary buffers, cached results, and Tk's copy can coexist. A limit on one buffer gives little guidance about peak process memory. [Core limits](../SafePdf/Core/Limits.lean) · [Viewer zoom and cache](../SafePdf/Shell/App/View.lean) · [Worker scheduling](../SafePdf/Shell/App/Viewer.lean)

### What can a document cause the application to do?

- **Navigate and change its presentation.** A local destination or `GoTo` action can change the page. The open-action handler ignores JavaScript, Launch, and remote actions. Clicking a URI shows its address and offers to copy it after confirmation. A document can request full screen, hide viewer controls, or put its own title in the title bar. Escape restores the controls. Those presentation choices matter when the reader needs to identify the file or distinguish a page from application UI. [Open settings](../SafePdf/Core/Doc/OpenSettings.lean) · [Link handling and window behavior](../SafePdf/Shell/App/Viewer.lean)
- **Supply text to search, copy, or index.** For page content with annotations disabled, `pageText_glyphs` ties extracted glyphs to the page's display list and fonts. Glyph provenance and positive-zoom coordinate round trips support selection and annotation placement. The Unicode mapping and replacement text can come from the PDF. Extraction includes invisible OCR text by default, and line order uses a heuristic. A search hit can therefore have a valid source in the document even when a reader cannot see that word on the page. [API theorem statements](../SafePdf/Api.lean) · [Text extraction and visibility policy](../SafePdf/Core/Text.lean)
- **Offer an embedded file.** Listing attachments does not decode their payloads. A tooltip probe has a 16 MiB per-stream limit. Saving decodes the selected entry, proposes a sanitized filename, and writes to the destination chosen in the dialog. The viewer provides no attachment execution path. The exported bytes retain the contents and risks of the original attachment. [Attachment model and filename properties](../SafePdf/Core/Doc/Attachments.lean) · [Viewer attachment policy](../SafePdf/Shell/App/Attach.lean)
- **Pass data across application boundaries.** Document-derived words sent through the Tcl command builder have quoting and round-trip proofs against a model of Tcl parsing. The C bridge checks image dimensions and available buffer length before passing pixels to Tk. The optional bib-lean mode adds real communication with a library server. It accepts a loopback origin, takes its bearer token on file descriptor 3, and bounds HTTP responses and request time. Annotation changes can sync before an explicit Save. Saving to the library can replace its PDF. [Quoting proofs](../SafePdf/Shell/App/TclLemmas.lean) · [Native bridge](../c/tk_shim.c) · [HTTP client](../SafePdf/Shell/App/BibLean/Http.lean) · [Library data flows](biblean.md)

### What happens to the original on Save?

An explicit Save can replace the opened file. The annotation writer appends a PDF revision. For a successful update, its proofs cover the original byte prefix, the affected object numbers, the planned annotation changes, and strict reopening. The shell checks the prefix and reads the marks back before writing. For an overwrite it checks for changes on disk, prompts on the first overwrite as applicable, and replaces the target via a temporary file and rename. XFDF import has a separate bounded XML parser that refuses DTDs and unknown entities. Its file helper uses the same metadata check followed by a whole-file read as the PDF library helper. [Writer proofs](../SafePdf/Spec/Write.lean) · [Save and read-back](../SafePdf/Shell/App/Save.lean) · [Overwrite flow](../SafePdf/Shell/App/Viewer.lean) · [XFDF import](../SafePdf/Shell/App/Xfdf.lean)

The prefix property has a privacy consequence. **Removing a note from the current revision can leave its old text recoverable in the file.** An annotated copy also retains the source PDF's embedded objects, including content safe-pdf ignores. Save provides revision integrity. Redaction, sanitization for third-party readers, and validation of a signer's approval of later edits would each require additional machinery. [Incremental writer](../SafePdf/Core/Write/Incremental.lean) · [Writer specification](../SafePdf/Spec/Write.lean)

The supported standard encryption handlers include legacy RC4 and AES, with empty user passwords. Permission bits are advisory. Encrypted updates use the document's existing handler, and the AES writer derives its IV deterministically. Identical plaintext at the same object position under the same derivation inputs can produce identical ciphertext across updates. Reopening verifies that the updated objects decrypt as planned. The cryptographic primitives have test-vector evidence, and the writer has no confidentiality proof for this construction. [Security handler](../SafePdf/Core/Crypt.lean) · [Writer encryption](../SafePdf/Core/Write/Encrypt.lean) · [Crypto tests](../Tests/Crypt.lean)

## How much evidence is there?

**Proofs.** For this review, `scripts/check-hygiene.sh` passed its source scan and checked the axiom dependencies of **1,052 listed declarations** using the checkout's built Lean modules. The strict scan covers Core, Spec, Repair, Api, and Quarantine. It rejects constructs such as `unsafe`, `partial`, panic-style indexing, and `sorry`. The axiom check allows `propext`, `Classical.choice`, and `Quot.sound`. The count describes the audit list. The Lean kernel checks the proof against its stated assumptions. The authors still choose what the specification says. The shipped binary also depends on the Lean-to-native toolchain, runtime, C bridge, Tcl/Tk, and operating system. For example, the Tcl quoting theorem applies to commands built with the quoted-word API. It cannot establish that every GUI call site uses that API correctly. [Guard rules](../scripts/hygiene.py) · [Audited declarations](../scripts/axioms.lean) · [Pinned toolchain](../lean-toolchain)

**Measurements.** The following are historical project runs recorded in the milestone ledger. Each measures a different property. The full corpus and GUI campaigns were not rerun for this assessment. [Milestone ledger](../progress.md)

| Recorded result | What it tells us |
|---|---|
| At milestone M3, the suite exercised 37 cases at a 1 MiB stream limit and again at 256 MiB. Oversized cases were rejected and near-limit controls passed. | Exercises the real decoder on both sides of a limit. The 256 MiB run is opt-in, so ordinary CI exercises the smaller setting. [Decompression suite](../Tests/Bombs.lean) |
| At `9bacf94`, qpdf agreed on 71,854 compared objects and page geometry across 81 files and 2,450 pages. | Independent evidence for object selection and page structure on that corpus. |
| At `7569011`, text similarity to MuPDF was 0.9949 over 2,436 pages. | At `b5da79e`, 2,435 of 2,450 pages passed the pixel comparison with MuPDF at 72 dpi. Only 11 were identical. | The perceptual threshold allows small differences. A small difference in a digit or symbol can still matter to a reader. [Pixel comparator](../Tests/differential/pixels.py) |
| At `3a225d6`, all 2,450 pages displayed in the viewer corpus run, with maximum measured peak RSS of 478 MiB. | An observed memory high-water mark for those files and that build. It gives a baseline for designing a desktop memory budget. [Viewer corpus protocol](viewer-corpus.md) |

**Repeatability.** The checked-in workflow builds the library, inspector, test and fuzz targets, runs the proof guard and a deterministic 2,000-iteration parser fuzz smoke, and compares objects, pages, and text with other implementations. The text job records similarity without enforcing the milestone threshold. Viewer, pixel, and position checks have scripts or proposed workflow steps outside the active CI jobs. A passing workflow therefore provides different evidence from a passing viewer milestone. ## How other projects address the same risks

| Project | Protection it offers | What that comparison means for safe-pdf |
|---|---|---|
| **SafeDocs and DaeDaLus** | DaeDaLus generates parsers from declarative format descriptions. Its authors report that the generated PDF parser came through the program's red-team exercise without a finding. The PDF Association's Arlington model provides an independent, machine-readable account of PDF objects. | safe-pdf has Lean theorems extending from syntax into rendering data and revision updates. An independent model can expose a mistaken assumption shared by its code and proofs. External review would complement its own fixtures. [DaeDaLus paper](https://doi.org/10.1145/3656410) · [DARPA program](https://www.darpa.mil/research/programs/safe-documents) · [Arlington model](https://github.com/pdf-association/arlington-pdf-model) |
| **Mozilla PDF.js** | Mozilla describes a worker parsing PDF data, a canvas rendering the page, and additional layers serving selection and forms. Its form-scripting design confines document JavaScript and omits PDF network and disk APIs. | PDF.js supports interactive workflows that safe-pdf deliberately narrows. Keeping document scripts out of safe-pdf removes an execution surface. PDF.js also illustrates why selection, visible appearance, and accessibility text deserve separate tests. [Mozilla's viewer architecture](https://hacks.mozilla.org/2021/10/implementing-form-filling-and-accessibility-in-the-firefox-pdf-viewer/) |
| **Chromium with PDFium** | Chromium designates its PDF component for sandboxed child processes. The embedding application supplies this protection. | A restricted process limits what a parser or renderer fault can reach. safe-pdf's worker threads share privileges with Tk and the shell. An OS boundary would protect the desktop even if an assumption below Lean failed. [Chromium PDF component](https://chromium.googlesource.com/chromium/src/+/main/pdf/README.md) |
| **Dangerzone** | A network-isolated converter renders a document to pixels. The host rebuilds a PDF from that narrow output. Original attachments, scripts, forms, and metadata drop out. Searchable text can be reconstructed with OCR. | For sharing a derivative with another reader, reconstruction addresses a threat that incremental Save deliberately preserves. For reading, searching, and annotating the original, safe-pdf keeps semantics that pixel conversion discards. [Dangerzone design](https://docs.dangerzone.rocks/latest/explanation/how-dangerzone-works/) · [Host–sandbox protocol](https://docs.dangerzone.rocks/latest/reference/sandbox-protocol/) |

## What to do next

| Priority | Change and reason | Acceptance criterion |
|---|---|---|
| **1 · Fix input and strict-mode boundaries** | Share the viewer’s capped-read approach with the PDF API, XFDF import, and the overwrite comparison. Thread the repair policy down to the strict opener. These are small changes at known call sites and reduce work before the caller can reject a file. | A growing input is read only through the configured cap plus one. A strict-only open records zero repair attempts. Existing compatibility mode still opens the same repair fixtures and reports them as repaired. |
| **2 · Isolate parsing and rendering** | Put the core and document-derived font and image processing in a restricted child process. Have the GUI broker file selection, clipboard, Save, and bib-lean access. Give the child only the input and explicitly supplied font data. Validate dimensions, lengths, and message types before allocating in the GUI. | A platform integration test verifies that the child cannot open unrelated files, use the network, or inherit the library token. Stopping a stalled worker leaves the GUI responsive and able to open the next file. |
| **3 · Budget a user operation across workers** | Reserve memory for simultaneous page buffers, thumbnails, and caches before dispatch. Carry a shared work allowance through a search, export, or render request. Select limits from measured desktop memory and latency targets. Enforce a worker memory ceiling and deadline independently of Lean's cost model. | A CI scenario interleaves zoom, search, and thumbnails. It records peak RSS and cancellation latency against published ceilings, reclaims reservations on failure, and successfully renders a normal page afterwards. |
| **4 · Make degraded or historical content visible to users** | Keep a trusted file identity and repair/incomplete-render indicator visible even when the PDF requests hidden controls. Expose invisible OCR and document-supplied replacement text in text exports where provenance matters. Explain revision retention at annotation deletion or export. | GUI and API tests cover a repaired file, an omitted image, invisible OCR, and an edited annotation. A reader can identify the source and missing content, and can tell whether a deleted note survives in prior bytes. |
| **5 · Review the writer's confidentiality and integrity boundary** | Have a cryptography reviewer assess encrypted updates. Supply fresh IVs from OS randomness at the shell boundary for AES writes and pass them into the pure writer. Set an explicit policy for legacy RC4 writes and signed or certified inputs. Review overwrite concurrency, temporary-file permissions, and persistence across interruption separately from the byte-prefix theorem. | Independent readers open and decrypt the new fixtures. Repeated AES writes use fresh IVs. Tests exercise the chosen signed-file policy, interrupted saves, and concurrent file changes, with expected disk outcomes recorded. |
| **6 · Test the shipped viewer independently** | Activate the existing viewer, position, and pixel checks on a pinned corpus. Extend ongoing fuzz coverage beyond parser entry points to decoders, render and save APIs, XFDF, and the native bridge. Run native memory/undefined-behavior checks. Commission a review of the proof statements, resource accounting, and shell boundary. | Release evidence names the commit, tool versions, sample sizes, exclusions, peak resources, and unresolved disagreements. Required jobs fail on regressions. Record the disposition of findings from the independent review. |

The capped reader and early strict-only routing are suitable for the next patch. The restricted worker and shared resource budget belong in the same design milestone. Together they let the application reject excessive work, recover from a failed render, and protect the user's files and library credentials while retaining the core's existing proofs.
